# S/Q 主机整段计费组件

2026-10-29。S GPU 入口复用审查发现 Q1 旧 f3 源的内层计费未覆盖主机独占准入、容器启动/退出和模式恢复。临时 CPU 账本反例表明：主机区间 20 秒时，旧解析器接受并结算了 10 秒内层账单。这些时间都是人工 CPU 夹具值，没有真实 GPU 执行或账本写入。当前控制器明确拒绝旧 f3；旧 stage 和回执未修改。

[新组件](../../../src/wcomr/sq_gpu_allocation_r1.py)由主机 guardian 持有唯一 monotonic 时钟，从准入前开始，到原容器确定终态及模式恢复后结束。监督器时间只能作为诊断；同一 deadline 包含准入耗时，并在启动前保留 180 秒完整释放余量。发生超限时保留实际成本，不截断账单。组件只生成原始账单和释放见证，不预约或结算中央账本。

Docker 观察只有确定的 no-such-container 响应才可判定未创建；UNKNOWN 和标签/UUID 不匹配不能停止或替换容器。原句柄一旦存在就只恢复。凭据缺失、准入失败、Popen 明确未 exec、子进程失败、超时与恢复失败都保留对应状态和费用。容器/模式任一终态未知时，账单明确标为不完整，中央 envelope 继续保留。

[受限 CPU 范围](ALLOCATION_CPU_R1.json)包含 12 项检查与八个实际 Linux CPU 子进程，含主机 guardian 的真实 SIGTERM 清理；GPU 模式和容器观察均为显式夹具，真实硬件/Docker 命令被拒绝，Torch 不导入。资源保持 2 CPU / 8 GiB / 1800 秒、隐藏 GPU、无网络、旧源只读、仅独立 stage 可写。两端从刚完成的物理矩阵 CPU 原 stage 接续，发布源码后恢复旧句柄，再独立接受。

此组件通过不代表 Q1 已修复完成。后续仍须把 Q1 guardian、监督器诊断、原件捕获、所有失败分支的财务终态及中央结算接入同一账单，完成受影响双端 CPU 后准备新的不可变执行 stage，并重新出具完整审阅。Q1 科学分母/原数值门/硬限保持，S 的完整 GPU 入口和整卡报价继续后置；本文件授予零 GPU 权限。

## 原 R1 与 R2 的 deadline 修复

两端原 R1 均完整退出 1，12 项中其余检查通过，但剩余等待时长仍使用容器创建前的值，未扣除启动耗时；原捕获和日志保留。原源为 `79827ffa`，没有真实 GPU 或账本动作。

[R2 CPU 范围](ALLOCATION_CPU_R2.json)在同一 monotonic deadline 上，于容器创建并写入原句柄后重新计算剩余时间；若启动已经耗尽释放余量，立即清理绑定的原 CPU 子进程并保留实际费用，不延长预算。新增该启动超时子情形，仍为 12 项检查、共九个真实 Linux CPU 子进程；180 秒释放余量与所有科学范围不变。两端只在确认原 R1 终态后使用独立 R2 stage，原 R1 不重派、不覆盖。
