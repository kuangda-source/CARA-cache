# WorldCache / CARA：配置、评价与统计口径讨论

日期：2026-10-27  
性质：基于已完成审计的讨论结论与后续报告规范；不是新实验结果或新GPU任务授权。

## 1. 当前判断

**目前以 Native 为参考的评价，适合衡量固定配置下的完整计算保真度；现有结果不能直接升级为优于论文官方 WorldCache 配置的结论。**

历史较高的 LPIPS 已经复算确认，同时也发现了生成配置和评分口径与论文不等价。两件事并存：分数不是凭空算错，但对应的基线不能笼统称为“论文官方配置”。

因此，保留已有数据、失败记录和评价门槛，修正基线称谓，优先补齐配置对齐和因果对照。不能因为基线分数较高，或官方论文也出现约0.5，就放宽 Native 保真要求。

## 2. 三种比较回答不同问题

设 N 为同请求完整计算的 Native 输出，W 为 WorldCache 输出，C 为我们的方法输出，G 为真实视频；d 表示一个明确固定实现和预处理的 LPIPS。

| 比较 | 回答的问题 | 不能直接推出 |
|---|---|---|
| d(W,N)、d(C,N) | 加速输出偏离完整计算输出多少 | 哪个视频更符合现实、物理规律或提示词 |
| d(W,G)、d(N,G)、d(C,G) | 在同一有真实参考的任务中，与真实视频有多接近 | 哪个方法更忠实复现 Native 计算 |
| 独立质量、物理或任务指标 | 生成视频的外观、运动、物理或下游任务表现 | 与 Native 的逐帧保真程度 |

Native 是计算参考，不是真实世界真值。某个输出更接近 Native，可以支持保真度改善；是否提升生成质量，需要对应的独立证据。

WorldCache 论文表6在 EgoDex I2V 上报告：Cosmos-Predict2.5-2B 的 Native 与 WorldCache 对真实视频的 LPIPS 均为 **0.518**。这只说明该表的汇总值在报告精度下相同，不说明两者视频相同，也没有给出 W 对 N 的距离。[论文表6](https://arxiv.org/html/2603.22286v1)

### 为什么不能把两个0.5相加

即使同一批数据、同一套 LPIPS 得到 d(W,N)≈0.5 和 d(N,G)≈0.5，也不能推出 d(W,G)≈1.0。距离不能沿两段比较直接相加；偏移可能在感知特征空间中方向不同。这里更不能把 LPIPS 直接当作满足所有数学距离公理的量来推导。

而本次讨论的两个约0.5还来自不同任务、不同参考和不同评分实现，更没有可加性。要知道对真实视频的误差，必须在同一任务上直接计算 d(W,G) 和 d(N,G)。

## 3. “官方配置”必须拆开说明

论文描述、README 示例命令、代码默认值、我们实际执行的配置不是同一个身份。后续结果须绑定实际配置和源码版本。

| 项目 | 历史本地运行 | 论文或官方评分代码 |
|---|---|---|
| 任务与参考 | CAL T2W，对同请求 Native 评分 | 论文表6是 EgoDex I2V，对真实视频评分 |
| 采样器 | UniPC/Karras | 论文描述 Euler |
| 步数 | 请求35，实际36步、72次CFG | 论文描述35步 |
| 缓存基础阈值 | 七场景 .06；两场景另扫 .08 | 论文 .08 |
| saliency 权重 | README显式参数1.0 | 论文 .12 |
| 光流空间缩放 | README显式参数2.0，实际先上采样 | 论文附录选择.5；源码默认也为.5 |
| ATS增长系数 | 实际horizon=70时，代码表达式得到5 | 论文beta_d=4 |
| LPIPS实现 | lpips0.1.4，AlexNet，metric version0.1 | 官方脚本调用piq.LPIPS()，默认VGG16 |
| LPIPS输入 | RGB float32，[-1,1] | RGB float32，[0,1]，内部标准化 |

两种输入范围各自符合其库的规范，不是归一化错误。不同骨干的分数不能当作同一量尺；不能以新的VGG数值直接套用原AlexNet门槛。

ATS差异是可追溯的源码推导：CFG将35写成70，代码取u=70/35=2，再计算u²/6+u/2+10/3=5。光流参数2.0也确实直接进入空间插值，不是“.5的倒数写法所以等价”。尚未通过新视频消融量化这些差异各自贡献了多少LPIPS。

固定WC版本为 `60a486df6d2e6d2aa3c21815895aac157a88e95d`。其缺失模型目录由NVIDIA版本 `a2c298b0a3df3778b973fe65e9e58877b292d8a7` 补齐，形成已披露的UniPC路径。9月30日的决策明确选择先完成当前公开代码技术对照，并未认定它是论文精确复现。

本次官方评分桥接固定PIQ 0.8.0；官方代码没有完整锁定论文当时的PIQ版本。因此它是按公开官方评分函数进行的明确版本重评分，不是作者原始环境的完全重建。

## 4. 约0.5的历史结果核查到了什么

本次核查16个原视频、9对视频、837个帧对。文件哈希、帧数、PTS及两种解码器的RGB结果一致。历史AlexNet分数逐帧最大复算差为 **2.98×10⁻⁸**。

| 样本 / 配置 | 原AlexNet复算 | 官方PIQ/VGG桥接 |
|---|---:|---:|
| industry，.06 | 0.532712 | 0.559247 |
| misc，.06 | 0.493993 | 0.510926 |
| human，.08 | 0.501563 | 0.520514 |
| 七场景.06等权均值 | 0.410505 | 0.461754 |

这些列都以 Native 为参考。换用官方评分实现后，偏移没有消失；也不能把两列大小之差解释为生成质量变化，因为评分对象未变，量尺变了。

已核实的配对证据包括：五组补生成Native的完整请求与旧WC一致，种子均为0，提示词、guidance、分辨率、帧数、权重路径/快照标识和实际时间步匹配；另两组有跨批视频逐字节相同的桥接证据。没有发现错视频、错种子配置或输入归一化导致的虚高。

仍有两个归因缺口：

- 五组Native是后来补生成，早期WC记录没有与后续Native相同的完整eval模式守卫；尚不能证明所有运行状态完全等价。
- 未找到同次运行“原生Native”与“缓存代码强制全计算”的完整视频零差异对照；旧批次也未完整保存初始噪声张量哈希。

因此，**可以确认旧高分真实可复算，不能声称已经排除所有运行路径因素。** 同批同eval的FAIR阈值扫描中，.04→.06→.08对应偏移持续增加，支持缓存设置确实影响保真度，但不能把它外推成论文配置下的误差结论。

## 5. 统一统计口径

### 5.1 先明确统计单位与分母

- 每个视频：对完整93帧的距离求算术平均，不抽帧、不裁剪、不改变历史尺寸。
- 多个场景：先求每个视频的均值，再按预先规定的场景权重汇总。历史七组使用等场景权重。
- 93帧不是93个独立场景；同一场景的不同阈值、重复运行或复用视频也不能增加独立场景样本数。
- 原CAL共有8个场景，接受7、拒绝1。七场景均值是接受子集的条件统计，必须同时报告8/7/1及拒绝原因，不能隐去失败分母或补换样本。
- 九对审计视频包含七组.06和两组.08，不能合成“九个独立样本的官方配置均值”。

后续若有多个种子，应预先约定如何在种子和场景之间聚合；置信区间也应尊重场景/种子的分组结构，不把帧当作独立样本来缩小误差条。

### 5.2 “改善百分比”必须说明分母

对同一匹配场景集合，设每个场景的基线Native距离为b_i，我们方法的距离为c_i。

整体均值相对改善：

```text
R = (mean(b_i) - mean(c_i)) / mean(b_i) × 100%
```

逐场景相对改善再平均：

```text
R_scene = mean((b_i - c_i) / b_i) × 100%
```

两者通常不相等，不能混用；b_i=0时后一式还需要预先规定处理规则。历史已冻结统计定义保持不变，不能事后选择更好看的公式。报告至少写明匹配样本数、两侧均值、绝对差和所采用的相对改善公式。

“LPIPS降低X%”指特定距离统计量的相对下降，不是“生成质量提高X%”，也不是“真实世界预测误差降低X%”。它更不是LPIPS下降X个百分点；LPIPS本身不是百分比。

### 5.3 保真、质量与速度分别报告

| 结论 | 所需证据 |
|---|---|
| 更接近Native | 同参考、同评分实现、同输入与生成配置的配对距离 |
| 更好的生成质量或物理表现 | 对应任务的独立质量/物理/真实参考评价 |
| 更快 | 匹配硬件、输入、精度、计时边界与运行条件的实测 |
| 更好的速度—保真折中 | 在匹配协议下同时报告速度与保真，明确比较工作点 |

减少完整计算次数、局部误差改善、带诊断的运行时间或成本模型估计，均不能单独替代端到端加速实测。

## 6. 我们目前可以怎样表述优化

固定本地配置下，只要候选与基线确实共享输入、种子、采样器、参考输出及评分协议，相对LPIPS下降仍然具有明确含义：候选更接近该配置下的完整计算输出。基线偏移较大，不会自动使相对改善失效。

但是，本次审计不是对全部CARA实验的重新验收；每项已有优化结论仍须绑定其自身完整回执、冻结对照和统计定义。不能把这九对历史视频的复核替代后续实验的公平性检查。

推荐表述：

> 在本文固定的Cosmos UniPC/Karras设置及匹配输入上，相比所采用的WorldCache公开代码配置，所提方法降低了相对完整计算Native输出的LPIPS。该结果衡量完整计算保真度；对论文配置的泛化和独立生成质量需另行验证。

目前不应表述为：

- 已经优于论文官方最优WorldCache配置。
- 仅凭Native LPIPS下降，证明生成质量或物理正确性更高。
- 本地WorldCache对Native约0.5，证明官方方法对真实视频的总误差很大。
- 官方表6也约0.5，所以本地保真门槛应放宽到类似数值。

**当前优化口径可保留，优势的适用范围必须收紧。** 基线代表性仍不足：收益中有多少属于稳定的方法改进，有多少依赖当前基线工作点，需要对齐后的对照回答。

## 7. 已确定的评价决策与后续验证顺序

1. 保留现有Native保真门槛、历史评分实现、原始结果和失败分母；不追溯修改验收。
2. 将旧基线明确命名为固定版本的“公开代码README参数技术对照”，附实际采样协议，避免泛称“官方默认”。
3. 官方PIQ/VGG作为桥接评分列保存；未来如新增评价协议，需单独版本化，不能把新量尺直接替换旧门槛。
4. 先验证同进程、同实测初始噪声、同eval/backend下的三臂：Native、WC代码强制全计算、实际WC。前两臂的一致性通过后，再判断缓存跳过造成的偏移。
5. 另行固定论文配置的Euler实现、完整sigma网格和参数映射，再做匹配生成。只修改num_steps并不等于完成Euler35复现；公开资料未完全明确的细节须显式记录。
6. 如比较论文表6，应使用相应EgoDex I2V输入及真实视频，同时报告Native–GT、WC–GT和WC–Native。独立质量评价可以补充保真评价，但不能据此事后豁免现有门槛。

以上是后续验证要求，不代表这些新生成或因果对照已经完成，也不自动授权新GPU任务。
